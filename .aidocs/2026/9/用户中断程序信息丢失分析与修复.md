# 用户中断程序后信息丢失：分析与修复

**日期**: 2026-09-10 | **关联任务**: [.aidocs/task/用户中断程序-信息丢失.md](../task/用户中断程序-信息丢失.md)
**分支**: `debug/scrapy_spider`

---

## 一、现象

用户手动 Ctrl+C 中断爬虫后，`spider_run_log` 表没有正常记录 request / pages 等信息，`status` 状态异常。日志片段：

```cmd
09:30:22 [INFO] scrapy.core.engine: Closing spider (shutdown)          ← 第 1 次 Ctrl+C
09:30:24 [DEBUG] scrapy.core.engine: Crawled (200) <POST .../articles>
09:30:24 [INFO] academic_spiders.spiders.pubscholar_v1: 桶 585e1dd6 第 7/126 页完成: 50 条
09:30:25 [DEBUG] scrapy.core.scraper: 第 7 页 文献: title=人工智能时代下的视频新闻发展及思考
09:30:25 [INFO] scrapy.crawler: Received SIGINT twice, forcing unclean shutdown   ← 第 2 次 Ctrl+C
```

两个疑问：
1. 为什么第一次 Ctrl+C（09:30:22）没有立即停止，反而继续运行到 09:30:25？
2. 为什么数据库 `spider_run_log.status` 显示为 `running`，但程序已经停止了？

---

## 二、验证：测试库 `spider_run_log` 数据

| id | start_time | end_time | status | req | items | last_page | 说明 |
|----|-----------|----------|--------|-----|-------|-----------|------|
| 14 | 2026-09-10 09:26:38 | **None** | **running** | 23 | 601 | 6 | ← 那次被中断的运行，至今停留 running |
| 13 | 2026-09-10 09:03:57 | 2026-09-10 09:04:35 | completed | 17 | 818 | 1 | 正常完成 |
| 12 | 2026-09-03 13:50:45 | 2026-09-10 09:03:55 | interrupted | 0 | 0 | 0 | end_time 是下次启动才补标 |
| 11 | 2026-09-03 11:56:04 | 2026-09-03 13:50:43 | interrupted | 0 | 0 | 0 | 同上 |

**关键观察**：
- `id=14` 就是被中断的那次运行（09:26:38 启动，运行至 09:30 被中断），至今 `status=running`、`end_time=NULL`；它有心跳数据（items=601），说明心跳正常跑过。
- 所有 `interrupted` 记录（id=1/2/11/12）特征均为 `req=0, items=0, last_page=0`，且 `end_time` 是**下一次启动时**由 `_mark_interrupted()` 补标的（如 id=12 的 end_time=09-10 09:03:55，正是 id=13 启动时补标）。
- 说明这些"中断"记录**从未走正常 `spider_closed` 流程**，是靠"下次启动兜底"才被标成 interrupted。
- `id=14` 之所以至今是 `running`，仅仅是因为它之后还没有新运行启动去触发兜底。

---

## 三、根因（核对 Scrapy 源码）

### 3.1 第一次 Ctrl+C 为何不立即停止

Scrapy 收到 SIGINT 走**优雅关闭**（`crawler.py:638` `_signal_shutdown` → `_graceful_stop_reactor`）：

```
engine.stop_async()  →  close_spider_async(reason="shutdown")  →  await self._slot.close()
```

而 `_Slot.close()`（`scrapy/core/engine.py:88`）：

```python
async def close(self) -> None:
    self.closing = Deferred()
    self._maybe_fire_closing()
    await maybe_deferred_to_future(self.closing)   # 等待所有在途请求清空

def _maybe_fire_closing(self) -> None:
    if self.closing is not None and not self.inprogress:   # inprogress 非空则不 fire
        ...
```

**优雅关闭会一直 `await`，直到 `self.inprogress`（所有在途请求）清空**。本爬虫桶内滑窗并发 `V1_BUCKET_WINDOW=4` 个在途请求，且去重管道（`MySQLPipeline`）写库较慢（日志大量"去重命中"），因此关闭需等待这些在途请求处理完 → 表现为 09:30:24/25 仍在 `Crawled`、产出 item。

> 补充：`parse_bucket_page` 在关闭期间只要桶未爬完（`is_last=False` 且 `page < max_page`）仍会调用 `_issue_pages()` 继续 `engine.crawl()` 发新请求（无"引擎正在关闭"检查），会进一步拉长优雅关闭时间，让用户感觉"按了 Ctrl+C 没反应"。

### 3.2 为何 status 停留 running

第二次 Ctrl+C 走**强制关闭**（`crawler.py:645` `_signal_kill` → `reactor.stop()`），**立即终止事件循环**，把 `await self._slot.close()` 打断：

- `close_spider_async` 中 `send_catch_log_async(signal=spider_closed, ...)`（`engine.py:644`）**永远不会执行**；
- 于是 `SpiderRunLogExtension.spider_closed()` 不被调用 → `write_run_end()` 不执行 → **记录停留 `running`**。

日志末行 `Received SIGINT twice, forcing unclean shutdown` 正是强制关闭的标志。

### 3.3 结论

`interrupted` 状态能出现，靠的是**下次启动时的 `_mark_interrupted()` 兜底**（`extensions.py`），而非关闭时正常写入。程序停止瞬间的 `running` 残留无法被该机制即时修复（它依赖"下次启动"）。

---

## 四、修复方案（B 方案：进程退出兜底）

> 按需求方选择：**不改动桶滑窗调度逻辑**（正常爬取行为不变），以"即使强制关闭也能落库"为核心。

在 `academic_spiders/extensions.py` 增加 **reactor 关闭兜底钩子**：

1. `__init__` 增加 `_finalized` 标志（防止重复落库）。
2. `from_crawler` 中注册钩子：
   ```python
   reactor.addSystemEventTrigger("before", "shutdown", self._on_reactor_shutdown)
   ```
3. `_on_reactor_shutdown()`：reactor 停止前**同步**落库（同步 pymysql，可在 shutdown 触发器中安全执行）。若 `spider_closed` 未触发（`_finalized=False`），则把记录写为 `status='interrupted'` + `end_time` + 兜底 error_message。
4. `write_run_end()` 成功时置 `self._finalized = True`，兜底钩子据此跳过，避免重复写入。

**原理**：reactor 的 `"before"/"shutdown"` 触发器在 reactor 停止前**必定执行**（优雅关闭与强制关闭都会走到），因此能覆盖"二次 Ctrl+C 强制关闭"这一 `spider_closed` 未触发的场景。

### 改动清单

| 文件 | 改动 |
|------|------|
| `academic_spiders/extensions.py` | 新增 `_finalized` 标志、`_register_reactor_shutdown_hook()`、`_on_reactor_shutdown()`；`write_run_end()` 成功时置 `_finalized=True` |

## 五、验证记录

### 5.1 单元验证（test 库）

| 场景 | 结果 |
|------|------|
| 正常关闭（`spider_opened` → `spider_closed`） | 落库 `interrupted`（reason=shutdown），`_finalized=True` ✓ |

### 5.2 端到端验证（reactor 钩子注册与触发）

- `reactor._eventTriggers['shutdown'].before` 中找到注册的钩子 → 注册成功 ✓
- `reactor.stop()` 后钩子被调用 1 次 → 强制关闭时会触发 ✓

### 5.3 编译

`compileall` 通过。`extensions.py` 中唯一 Pylance 报错为 Twisted 类型存根将 `eventType` 误标为 callable 的类型噪音（Scrapy 自身 `crawler.py:699` 亦如此调用），运行时正常。

## 六、注意事项

1. **对历史脏数据无效**：兜底钩子只对"新运行"生效。测试库中遗留的 `id=14` running 记录，会在下次启动时被 `_mark_interrupted()` 自动补标为 interrupted，无需手动处理。
2. **未改桶调度**：按需求选择"关闭期间保持滑窗发请求，仅靠等待 inprogress 清空"，本次未改动 `_issue_pages`/`_try_dispatch_buckets` 逻辑。
3. **可选的后续增强（未实施）**：
   - A 方案：关闭期间停止发起新请求，缩短优雅关闭时间（让 `spider_closed` 更快触发）；
   - 信号提示：在信号处理层提示"优雅关闭中，请稍候；再次 Ctrl+C 将强制退出"。
