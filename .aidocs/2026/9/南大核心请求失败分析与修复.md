# 南大核心请求失败：分析与修复

**日期**: 2026-09-09 | **关联任务**: [.aidocs/task/南大核心期刊请求失败.md](../task/南大核心期刊请求失败.md)
**分支**: `debug/scrapy_spider`

---

## 一、现象回顾

生产环境（prod）分桶模式先处理完"北大核心"，切换处理"南大核心"时，所有桶请求返回异常（HTTP 200 但 `total_pages=0`、内容为空），连续 6 次后整桶失败：

```bash
2026-09-08 10:52:03 开始爬取桶: qhash=df429f2f, total=568, max_page=12,
                    filters={'lang':'C','year':'2019','subject':'投资经济、股票','collection':'南大核心'}
2026-09-08 10:52:12 桶 df429f2f 第 4 页响应异常 (total_pages=0), 重试 5/5
2026-09-08 10:52:13 桶失败: qhash=df429f2f, 原因=连续异常响应 6 次
```

**初步怀疑**: 分桶构建时对"南大核心"处理有问题；网页端发现 collection 下已不存在"南大核心"选项，似乎改成了 `CSSCI`。

---

## 二、验证方法与证据

### 证据 1：线上聚合接口可选项已改名

用 `collection=` 为空（base）请求聚合接口，返回的 collection 维度可选项已**没有 "南大核心"**，只有 `CSSCI`：

| 旧 response.json（改版前） | 线上现状（2026-09-09） |
|---|---|
| `南大核心`（≈1,649,432） | `CSSCI`（≈1,646,597） |
| 另有零散 `CSSCI`（仅 64 条，过渡残留） | "南大核心" 已完全消失 |

> `.aidocs/academic-spiders/response.json` 中同时出现 `南大核心`(1.6M) 与 `CSSCI`(仅 64)，正是网站改名过渡期残留：主体用"南大核心"，旧标签 `CSSCI` 只剩零星脏数据。如今网站已彻底迁移到 `CSSCI`。

### 证据 2：用旧值过滤 → 空；用新值 → 完整

对**生产日志中失败桶的查询参数**做对照请求：

```
year=2019, subject=投资经济、股票   (即日志中 df429f2f, total=568, max_page=12)
  collection=南大核心  -> total=0      content=0   is_last=true      ← 站点不认识该值
  collection=CSSCI     -> total=568    total_pages=12 content=50 is_last=false  ← 正常!
```

另验证 `心理学`、`year=2026` 等桶同样成立。即：**用 `CSSCI` 重跑完全相同的桶即可拿到完整数据。**

### 证据 3：测试库确认"当时能跑"

查询 `academicdb_test.crawl_query_state`：

- 存在 2026-08-25 / 08-31 构建的 `collections=南大核心`、`collections=北大核心,南大核心` 计划；
- 南大核心桶在 **2026-09-03** 仍有大量 `completed`（如 2019/管理学 total=831 等）→ 说明 09-03 时站点还认 "南大核心"。

---

## 三、结论（根因）

**不是分桶逻辑坏了，而是站点在 2026-09-03 之后，把 collection 取值从 "南大核心" 更名成了 "CSSCI"。**

- `CSSCI` = 中文社会科学引文索引（南京大学核心），与"南大核心"**本质是同一个集合**，只是换了标签。
- 用旧值 `南大核心` 作为过滤参数时站点**不认识**，所有分页均返回空（`total_pages=0`），触发"连续异常响应 6 次"而整桶失败。
- `北大核心` 未受影响，故先处理的部分正常。

**正确做法**: 目标集合取值改为站点当前的 `CSSCI`（北大核心不变）。

---

## 四、已落地的代码修复

统一把"目标集合"取值从 `南大核心` 改为 `CSSCI`：

| 文件 | 改动 |
|---|---|
| `academic_spiders/spiders/pubscholar_v1.py` | 默认 `bucket_collections=["北大核心","CSSCI"]`、`raw_collections` 回退值、改名注释 |
| `academic_spiders/settings.py` | `V1_BUCKET_COLLECTIONS` 默认 `北大核心,CSSCI` + 注释 |
| `academic_spiders/utils/query_plan.py` | 模块注释 |
| `fetch_aggregations.py` | `CORE_COLLECTIONS=["北大核心","CSSCI"]` + 用法 |
| `verify_window_limit.py` | `CORE_COLLECTIONS=["北大核心","CSSCI"]` + 上下文标签 |

已编译通过；`settings` 读取确认默认值为 `北大核心,CSSCI`。仍可用环境变量覆盖：
`V1_BUCKET_COLLECTIONS=北大核心,CSSCI`（或站点当前任意有效值）。

## 五、生产/测试操作脚本

### 关键点：必须先清理旧标签遗留桶

分桶领取逻辑 `QueryStateStore.claim_next()` **按 id 顺序领任意 pending 桶、不过滤 collection**。因此：

- 代码默认值改动后，`crawl_plan` 的 plan_key 因集合字符串变化而自动失效 → 下次运行会自动重建（无需 `V1_BUCKET_FORCE_PLAN`）；
- 但**旧计划遗留的 `南大核心` pending 桶（id 更小）会被先领走**，再次全部空返回而失败，把新 `CSSCI` 桶堵在后面。

### 5.1 清理数据库（测试库 / 生产库各执行一次对应库的脚本）

```sql
-- 测试库 (academicdb_test)
USE academicdb_test;
-- 删除旧标签 "南大核心" 的残留桶 (该值已死, 永远爬不到)
DELETE FROM crawl_query_state
 WHERE JSON_UNQUOTE(JSON_EXTRACT(query_params,'$.collection')) = '南大核心';
-- 可选: 删除旧 "南大核心" 集合的计划标记 (集合名改变后 plan_key 已变会自动重建, 删除更干净)
-- DELETE FROM crawl_plan WHERE FIND_IN_SET('南大核心', collections);
```

```sql
-- 生产库 (pubscholar)
USE pubscholar;
DELETE FROM crawl_query_state
 WHERE JSON_UNQUOTE(JSON_EXTRACT(query_params,'$.collection')) = '南大核心';
-- DELETE FROM crawl_plan WHERE FIND_IN_SET('南大核心', collections);
```

> 注意：`北大核心` 桶（已完成/进行中）不受影响，**请保留**，不要误删。

### 5.2 测试库先验证（推荐）

```bash
# 切到测试模式
python env.py switch test
# 在 academicdb_test 执行上述"测试库"清理后，限爬 3 桶验证 CSSCI 桶能真实落库
scrapy crawl pubscholar_v1 -s V1_BUCKET_MODE=1 -s V1_BUCKET_MAX_BUCKETS=3
```

观察点：应看到 `collection: 'CSSCI'` 的桶正常翻页返回内容，不再出现 `total_pages=0` 的异常重试与整桶失败。

### 5.3 生产库正式续爬

```bash
# 切到生产模式 (需二次确认或 -y)
python env.py switch prod -y
# 在 pubscholar 执行上述"生产库"清理后，分桶续爬 (会自动重建 CSSCI 计划并从 CSSCI 桶开始)
scrapy crawl pubscholar_v1 -s V1_BUCKET_MODE=1
```

## 六、后续建议

1. 本次根因是站点改动字段取值。分桶顶层 collection 目前为硬编码默认值（可用 env 覆盖）。若要更强健，可考虑让顶层集合取值**从聚合响应动态读取**，避免站点再次改名导致整批白跑（属较大结构调整，本次未实施）。
2. 若对"新 CSSCI 与旧南大核心是否有重叠 / 是否按 `dedup_key` 去重"有疑问，需另行确认。
